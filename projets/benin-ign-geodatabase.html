De 77 géodatabases IGN à une base relationnelle unique

Consolidation du fonds cartographique de l'IGN Bénin dans une base benin_ign

Contexte et objectif

Le fonds topographique brut de l'Institut National de l'information Géographique du Bénin est organisé en douze départements, chacun subdivisé en communes, chaque commune stockée comme une géodatabase ESRI (.gdb) indépendante — soit 77 géodatabases au total. L'objectif était de tout regrouper dans une seule base de données relationnelle PostgreSQL/PostGIS, robuste et interrogeable. La difficulté principale : ces 77 fichiers ont été saisis sur près d'une décennie par des équipes différentes, chacune avec ses propres conventions de nommage et de typage des données.

Démarche et outils

1. Audit — 199 noms pour 45 thèmes

Avant d'écrire la moindre ligne d'import, un script Python (module fiona) a parcouru les 77 géodatabases pour lister toutes leurs couches. Résultat : 199 noms de couches distincts pour un nombre réel de thèmes bien plus restreint (écoles, routes, cours d'eau, zones inondables...), à cause de quatre sources de désordre accumulées commune par commune : des variantes de casse (route / Route), des fautes de frappe (cours_deau / cours_deeau), des résidus de traitements QGIS antérieurs (couches _Clip, _1, _select), et une nomenclature à part utilisée par le département de l'Ouémé.

Le piège : l'hypothèse de départ (les couches _Clip sont de simples doublons à ignorer) s'est révélée fausse dans quinze communes du Couffo et du Zou, où cette version _Clip était la seule copie existante de la couche. La résolution des doublons a donc dû se faire commune par commune, jamais par un motif de nom appliqué globalement. Après correction, les 199 noms bruts se résolvent en 48 thèmes canoniques, formant un plan d'import de 3 114 entrées (une par couple commune × thème réellement présent).

audit_schema.py — extrait

for dept, name, path in gdbs:
    commune_key = f"{dept}/{name}"
    layers = fiona.listlayers(path)
    for l in layers:
        with fiona.open(path, layer=l) as src:
            layer_geom[l].add(str(src.schema["geometry"]))
            for fname, ftype in src.schema["properties"].items():
                layer_fields[l][fname].add(ftype)
            layer_presence[l].append(commune_key)

print(f"Distinct layer names across all communes: {len(layer_fields)}")

2. Import — quand l'outil standard ne suffit pas

La voie naturelle pour charger des géodatabases ESRI dans PostGIS est ogr2ogr. Premier obstacle : la copie de GDAL livrée avec l'installateur PostgreSQL n'embarque pas le pilote d'écriture PostgreSQL, seulement un export SQL (PGDUMP). Retour à Python, avec GeoPandas et SQLAlchemy pour piloter l'écriture directement via psycopg2. Deux problèmes de fond sont apparus en cours de route : des types incohérents d'un même attribut d'une commune à l'autre (résolu en convertissant tout en texte à l'import, puis en retypant proprement une fois en base), et surtout un bug plus coûteux — geopandas.to_postgis() déduit le type de la colonne géométrie à partir du premier lot inséré et ignore silencieusement tout dtype passé explicitement. Si la première commune traitée pour un thème a une couche vide ou 2D, la table se fige et tout le reste de l'import échoue avec Geometry has Z dimension but column does not.

La parade : créer la table à la main, avec une colonne géométrie générique et toujours 3D, puis n'utiliser que if_exists='append' pour que GeoPandas ne touche plus jamais au schéma.

run_import2.py — extrait

col_defs = ", ".join(f'"{c}" text' for c in col_union)
create_sql = (
    f'DROP TABLE IF EXISTS ign."{theme}"; '
    f'CREATE TABLE ign."{theme}" ('
    f'gid serial PRIMARY KEY, {col_defs}, '
    f'departement text, commune_src text, geometry geometry(GeometryZ,32631))'
)
with engine.begin() as conn:
    conn.execute(text(create_sql))

# geometry forcée en 3D avant écriture, pour que la dimension
# de la colonne ne dépende jamais de la commune écrite en premier
gdf["geometry"] = gdf["geometry"].apply(
    lambda g: shapely.force_3d(g) if g is not None else None
)
gdf.to_postgis(theme, engine, schema="ign", if_exists="append", index=False)

Résultat : 3 114 / 3 114 couches importées, 0 échec, 909 429 lignes au total, 48 tables thématiques créées.

3. Finaliser le schéma — index, clés, types

Trois passes automatisées ont transformé l'ensemble de tables importées en un vrai schéma relationnel : un index spatial GIST sur la colonne géométrie de chaque table ; la table ign.commune (77 lignes) promue référentiel communal via une contrainte UNIQUE(commune_src), une nouvelle table ign.ref_departement (12 lignes), puis une clé étrangère commune_src → ign.commune posée sur les 47 autres tables (0 valeur orpheline détectée) ; et un script de cast qui scanne chaque colonne texte et la retype en bigint ou numeric si toutes ses valeurs non nulles sont numériques — 49 colonnes sont devenues des identifiants, 67 des mesures, 396 sont restées en texte parce qu'elles le sont réellement.

cast_numeric.py — extrait

for c in cols:
    total, non_null, matches_int, matches_num = conn.execute(text(f'''
        SELECT count(*),
          count(*) FILTER (WHERE "{c}" IS NOT NULL AND "{c}" <> ''),
          count(*) FILTER (WHERE "{c}" ~ '{INT_RE}'),
          count(*) FILTER (WHERE "{c}" ~ '{NUM_RE}')
        FROM ign."{t}"
    ''')).fetchone()

    if matches_int == non_null:
        conn.execute(text(
            f'ALTER TABLE ign."{t}" ALTER COLUMN "{c}" TYPE bigint USING NULLIF("{c}", \'\')::bigint'
        ))

4. Un vrai bug de données, trouvé en connectant QGIS

En chargeant les 49 tables dans QGIS, une seule a refusé de s'afficher : limite_administrative, qui mélangeait 378 lignes et 20 polygones — QGIS n'accepte pas une géométrie de type mixte dans une même couche. Les 20 polygones provenaient tous de dix communes du Couffo et du Zou, là même où la source utilisait la nomenclature _Clip évoquée à l'étape 1 : dans ces communes, la couche encodait autre chose qu'une simple limite linéaire. Solution : séparer proprement en deux tables homogènes, reliées par la même clé étrangère vers commune.

séparation limite_administrative — SQL

BEGIN;
CREATE TABLE ign.limite_administrative_zone AS
  SELECT * FROM ign.limite_administrative WHERE ST_GeometryType(geometry) = 'ST_MultiPolygon';
DELETE FROM ign.limite_administrative WHERE ST_GeometryType(geometry) = 'ST_MultiPolygon';
ALTER TABLE ign.limite_administrative_zone ADD PRIMARY KEY (gid);
CREATE INDEX idx_limite_administrative_zone_geom ON ign.limite_administrative_zone USING GIST (geometry);
ALTER TABLE ign.limite_administrative_zone ADD CONSTRAINT fk_limite_administrative_zone_commune
  FOREIGN KEY (commune_src) REFERENCES ign.commune(commune_src);
COMMIT;

5. Connecter QGIS et pgAdmin

Le protocole QGIS-MCP, déjà mis en œuvre pour piloter QGIS par langage naturel dans un autre projet, a servi ici à automatiser le chargement des 49 couches dans un groupe de calques via l'API PyQGIS, puis l'enregistrement d'une véritable connexion PostgreSQL native (via QgsProviderRegistry), visible dans le Navigateur au même titre qu'une connexion créée à la main. Côté pgAdmin, le Geometry Viewer restait obstinément vide : toutes les géométries avaient été forcées en 3D pendant l'import (étape 2), et le rendu Leaflet de pgAdmin gère mal la dimension Z — un bug connu, sans lien avec la validité des données. Plutôt que de corriger requête par requête, la base entière a été reconvertie en 2D avec ST_Force2D(), appliqué aux 49 tables spatiales sans casser un seul index.

force_2d.py — extrait

for t in tables:
    conn.execute(text(
        f'ALTER TABLE ign."{t}" ALTER COLUMN geometry '
        f'TYPE geometry(Geometry,32631) USING ST_Force2D(geometry)'
    ))

6. Modéliser : du sens métier au schéma physique

Une fois la base stable, restait à la documenter proprement en Merise, à deux niveaux de lecture. Le Modèle Conceptuel de Données capture le sens métier indépendamment de l'implémentation : un département comprend des communes, chaque commune localise des objets géographiques — une entité générique qui se spécialise (contrainte T, totale et exclusive) en 48 types concrets. C'est aussi le seul niveau où l'arrondissement existe comme entité à part entière ; physiquement, il est fondu dans les tables arrondissement_polygone / arrondissement_ligne. Le Modèle Physique de Données reflète le schéma réel : chaque table thématique porte un identifiant gid, ses attributs propres, une clé étrangère commune_src et une colonne geometry typée et indexée en GIST.

Résultats

La base benin_ign tient aujourd'hui dans un schéma unique, ign : 50 tables (49 spatiales en 2D EPSG:32631, plus le référentiel ref_departement), 909 429 entités réparties sur ces tables et chacune tracée jusqu'à sa commune d'origine, 49 index GIST avec une clé primaire et une clé étrangère par table thématique, une connexion PostgreSQL native persistante dans QGIS et une base lisible dans pgAdmin. Le chantier suivant, s'il a lieu : normaliser plus loin les 396 colonnes texte restantes — des champs comme type, nature ou source répètent les mêmes valeurs sur des milliers de lignes et gagneraient à devenir de vraies tables de référence.
